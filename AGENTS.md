# Standard ASR

Standard ASR is a **Python library that defines and enforces a universal interface protocol for ASR (speech-to-text) inference**. Think USB-C for speech recognition, or what the OpenAI Chat Completion API did for LLMs: once a protocol becomes the common language, any new engine that adopts it is **instantly usable by every application in the ecosystem** — and any application that speaks it can use **any compliant engine** without changing a line of code.

**What this repo contains:**
- A **runtime library** (`standard-asr`). `contract` holds the protocol data model every party shares. `runtime` runs each request against the chosen engine. `audio` turns any user input into engine-ready audio. `plugins` finds installed engines through entry points. Each package's docstring describes that package in more detail. `README.md` shows what the library does today.
- A **toolchain**, in the `toolchain` package and `compliance.py`: a CLI (its `doctor` subcommand diagnoses plugin dependency conflicts), a FastAPI server that exposes any engine over HTTP and WebSocket, and a compliance test suite.

**What this repo does not contain:** speech recognition code, model weights, or training. We build the bridge, not the endpoints. Each engine is a separate pip-installable plugin package (for example, `std-faster-whisper`, `std-mlx-audio`) that implements the standard interface.

**We are in the pre-release stage.** Always choose the long-term optimal design over backwards compatibility.

## Stakeholders — consider all three in every decision

- **App developers** (primary users): every ASR engine through one stable interface, no vendor lock-in, zero-config discovery.
- **ASR engine authors**: a low barrier to getting an ASR engine into users' hands. Implement one interface. The CLI, the reference server, and the compliance tests come for free — the engine works with every Standard ASR application on day one, with no per-app integration. Focus on models, not plumbing.
- **End users**: choose the best ASR for their language, domain, and hardware — install a plugin and use it immediately, with no app changes.

## Principles

`docs/content/mission.md` is the authority for the project's philosophy. This file restates the principles a contributor decides by, and adds what only matters inside the repository. A change to a shared principle is made in `mission.md` first and carried here in the same change.

- **Single source of truth.** Every fact has one authority: the one place that defines it, and the place you edit when the fact needs a change. Each kind of fact has its own. The pages under `docs/content/specification/` say what the protocol, the wire API, the CLI, and the download policy require. A type signature and its docstring say what the Python API promises. How the library keeps that promise lives in the code. A number or a default is written once, where it is owned: a value that more than one place uses is a named constant, and a field's default stays on the field. `TERMINOLOGY.md` owns the project's terms and points at the code that owns each controlled vocabulary. Everything else is a copy. A copy is fine where a reader needs the fact, as long as it repeats only the part that reader needs, says where the authority is, and gets checked against it. Two copies nobody checks drift apart. When two places disagree, start from the problem each place solves, from first principles, and work out which one is the design we meant. If the design itself missed the case, say so.
- **App developer first.** When the three stakeholders pull in different directions, the app developer wins. Zero-config, zero-surprise, zero-ambiguity. Batteries included where they help (audio loading, SRT/VTT renderers), but heavy dependencies stay optional (`[audio]`, `[server]`).
- **Explicit > implicit.** Whatever happens, show it: no swallowed errors, no silent degradation, no fake success, no hidden data flows. Silent wrong results are the cardinal sin. When in doubt, fail loudly or emit a structured diagnostic. A warning says what can go wrong and what to do about it, in a tone that matches the real risk. Convenience never means silence: do the helpful thing and say what we guessed or lost. When nothing helpful can be done, fail loudly: an error the developer can fix beats a silent wrong transcript.
- **Standard-library rigor.** This is infrastructure others build on for 10 years. Design and write it like the standard library. A developer should be able to learn the behavior from the documentation and signature alone, without reading the implementation. Every name is a design decision.
- **Long-term optimum.** Decide like the person who maintains this for the next ten years. Pick the design that is best for all three stakeholders over that span, and never keep a worse one because the better one is more work; effort estimates are always wrong. But the complexity a design keeps forever is part of the design, not part of the effort, so a bigger design has to justify itself against the smaller one that would also work. The optimum sets the destination, not the step size: land the work in small, reviewable steps.
- **Reason from first principles.** To make, understand, review, or revisit a technical decision, start from the problem it solves, not from the pattern that looks familiar. "Why is it designed this way?" is a legitimate question at any time — ask it, and challenge the answer. Every unclear premise must be resolved, not worked around. This questioning is welcome: it leads to better decisions and finds real problems. That includes the rules in this file: a rule followed against its own reason is a defect, so when a rule and its reason part ways, say so and fix the rule.
- **Trust model: plugins are trusted code; data from outside is not.** The application, this library, and every installed plugin are one party. Nothing here can stop a plugin that means harm, so we defend against accidents, not adversaries. Data from outside is untrusted: whatever the application takes from its users, and every request the reference server receives. Authentication and rate limiting belong to the deployment. The operator is trusted, but the library never reads a safety switch such as `allow_private_urls` from an environment variable: a check turned off there is a check nobody sees. Before adding a defense, ask who it stops and whether it is ours to stop. `runtime/redaction.py` owns the secret-handling rules and says what they leave open.

## Conventions

- A platform- or hardware-specific feature is optional: the core runs everywhere, and where the feature is unavailable the user gets a graceful fallback or a clear error. CI covers macOS, Windows, and Linux.
- Before you call a change done, run `prek run --all-files` and `uv run pytest` (`CONTRIBUTING.md`, "Git hooks (prek)"); the test suite is a push hook, so `prek run` does not run it.
- A new dependency needs a compatible license, active maintenance, and scrutiny of its supply chain; prefer the standard library and existing dependencies (`CONTRIBUTING.md`, "Dependency policy").
- The CLI's output is its interface: `toolchain/cli.py` prints results to stdout and errors to stderr, and no log line goes to stdout.
- Documentation lives in `docs/`. `docs/content/` is the published site content: every Markdown file under it ships, each page needs a frontmatter `title`, links between pages use explicit relative paths (`./other-page.md`), and raw HTML fails the build. `docs/internal/` never ships. The documentation website is its own program under `docs/site/` (TypeScript; Node and pnpm; its own linters in CI), so the prose standard does not apply to its code. The English it renders on its own pages, such as the home page's copy and code samples, is a front-door surface: governed for accuracy and terminology by review, because Vale cannot read TypeScript (`STYLE.md`, "Scope"). It generates the API reference from docstrings, so a docstring or function change needs nothing from it. A new Python module that should appear in the reference needs two things: an entry in `MODULE_PAGES` (`docs/site/scripts/dump_api.py`) and a page under `docs/content/reference/` naming it in `api_module`; the build fails if either is missing. Read `docs/site/README.md` before changing the site itself.

## Writing

- **Write for a stranger.** Your reader knows software but has never seen this project. That holds for everything you write, in any language, including the Chinese specification and the working notes. Write in plain words, the way people talk, not in jargon or AI slop. Our own terms come from [`TERMINOLOGY.md`](TERMINOLOGY.md) or from a name in the code. Explain anything else the first time you use it, or find a plainer word.
- **Check every claim about the code against the code.** Where an authority settles a change, name the defect in the commit message and cite that authority by path and line. Where none does, the change is a design decision: state the decision and its reason, and change the authority itself.
- English for all code, comments, and logs. Commit messages are imperative and concise, one logical change per commit. In Markdown, do not wrap lines at a column width; let the editor wrap.
- [`STYLE.md`](STYLE.md) is the standard for English writing in this repository. It covers docstrings, comments, runtime strings, Markdown, and what you write on GitHub, commit messages included. The exact list is its "Scope" section. The checklist at its end names every rule in one line, so read it before you write. The standard is built for English, so the Chinese documents sit outside it. A wrong translation of a specification is worse than a late one, so they stay Chinese. Everything above still applies to every line you add to them.
